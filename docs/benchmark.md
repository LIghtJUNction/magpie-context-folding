# 递归折叠、费用和性能测试

2026-10-26 的 v0.1.0 本机结果，未包含后来 v0.2.0 增加的响应统计回调开销。原始测量及计价字段集中在 [benchmark-results.json](benchmark-results.json)，复现脚本在 `scripts/`，不逐次保留日志、存档或输入副本。

## 已验证的功能

本地 36 项测试通过，另用真实 Magpie 0.1.1578 / Bun 的 HTTP 和 MCP 接口验证了加载、标记、自动折叠、两层展开、原文校验、禁止折叠、拒绝亏损和会话隔离。

专门的递归工作负载实际完成 **原文 → 第一层 → 第二层 → 第三层 → 第二层 → 第一层 → 原文**。重复发送 9 次不增加层数，重新固定原文后再次使用同摘要会复用已有层。Unicode 原文包括孤立 UTF-16 代理也能无损存取。

三次折叠的集成计费服务使用明确的人工模型：序列化字符为 token、所有输入档位同价。它用于检验三层机制，不能冒充真实渠道的费用证明。参考价格下不划算的递归层单独列在下面。

## 经济计算

对 650 条历史记录，真实 `o200k_base` 文本分词结果为：

| 版本 | 文本 token | 相对原文减少 |
| --- | ---: | ---: |
| 原文 | 16,955 | 0% |
| 第一层 | 637 | 96.24% |
| 第二层 | 467 | 97.25% |
| 第三层 | 300 | 98.23% |

这些是提供给分词器的文本 token，包含折叠版管理提示，但不等于某个供应商完整 API 计费输入。

价格示例采用 2026-10-26 查到的 GPT-4.1 标准文本费率：输入 $2、缓存读取 $0.50、输出 $8 / 百万 token；该模型页面标为 Deprecated，只作计价参考。[官方模型价格](https://developers.openai.com/api/docs/models/gpt-4.1)、[官方缓存规则](https://developers.openai.com/api/docs/guides/prompt-caching)

按“旧版本全部走缓存、新版本全部按普通输入价重算”的条件计算：

| 本次变换 | 仅输入的费用差 | 严格门槛 |
| --- | ---: | --- |
| 原文 → 第一层 | 节省 $0.0072035 | 通过 |
| 第一层 → 第二层 | 增加 $0.0006155 | 拒绝 |
| 第二层 → 第三层 | 增加 $0.0003665 | 拒绝 |

所以允许递归折叠不等于每次递归都应该执行。插件对每次候选重新检查，不拿第一层的收益掩盖下一次的亏损。

原文和最终层的**一次请求**比较，是另一种视角，不能与上表三个增量相加：最坏缓存条件下，文本输入节省 $0.0078775。三次标记的测试参数共 748 个输出 token；假设这些参数由按参考价计费的模型生成，其输出预算为 $0.005984，扣后剩 **$0.0018935**。这没有计算未知的额外标记输入轮次或回答输出变化，不能称全任务保证盈利。

再预留一次完整原文展开的 16,955 个输入 token，需 $0.03391，净值变成 **−$0.0320165**。小样本按同样最坏缓存条件也不能覆盖三次标记预算。失败结果保留，不靠假定未来一定继续请求来摊销。

数学放行规则为 `G = (L × p_min − U × p_max) / 1e6 − H > 最低节省金额`，完整推导见 [economics.md](economics.md)。只有可信 accounting 覆盖最终计费输入与后续路由转换时，才构成真实费用的充分保证；这里的文本计算不是生产计费证书。

## 真实性能测量

本机已有 Ollama 0.20.2、`smollm2:135m` F16，原生上下文 8,192，测试设为 4,096。相同输入工作负载、温度 0、seed 42、4 线程、输出 1 token；禁止截断，所有请求的输入计数均低于上下文限制。首次载入及预热不计入结果。

四个版本交替测试，每格 5 次，两种场景共 40 次有效测量，传输或推理执行错误 0。前缀扰动场景给同一组版本加相同随机前缀，削弱历史前缀复用；服务端没有缓存 token 计数器，因此不声称绝对零缓存。热缓存场景先立即发送相同请求预热，再测重复请求。

| 版本 | 本模型输入 token 中位数 | 前缀扰动：总耗时中位数（范围） | 热缓存：总耗时中位数（范围） |
| --- | ---: | ---: | ---: |
| 原文 | 1,913 | 173.78 ms（164.04–206.99） | 52.32 ms（42.10–78.58） |
| 第一层 | 759 | 88.06 ms（59.31–105.05） | 39.24 ms（35.58–85.51） |
| 第二层 | 588 | 77.13 ms（42.46–97.98） | 58.26 ms（36.91–61.98） |
| 第三层 | 422 | 82.77 ms（41.40–157.60） | 44.59 ms（36.66–68.70） |

前缀扰动下，第三层相对原文耗时中位数减少 **52.37%**，约 2.10 倍；热缓存范围重叠，第二层中位数还更慢，**不能证明热缓存下稳定提速**。

服务端原文输入处理阶段中位数为 139.92 ms，约占服务端总耗时 80.8%；独立 profile 的原文输入处理 144.60 ms、第三层 57.96 ms，加载阶段约 29.10 / 26.97 ms。观察到的主要节省来自减少输入处理工作，不是跳过失败请求。测试时存在其他工作和 I/O 压力，swap 已用约 18 GiB；因此同时保留范围，不对生产模型或其他硬件外推倍数。

上述推理测量直接请求 Ollama，未把 Magpie 网关和插件时间混入。插件的独立稳定重放开销在小样本为 **1.78 ms** 中位数，9 次范围 1.47–3.34 ms；大样本为 **2.16 ms**，范围 1.93–3.17 ms。把二者中位数相加只是预算估计，不是完整链路实测。

这个小模型在单 token 模式下没有正确回答预期的 `OK`：原文输出 `The`，折叠版输出 `[`，精确符合预期 **0/40**。这验证的是实际输入处理与传输开销，**不是有用任务完成速度或语义质量测试**。可逆恢复已经验证，摘要质量及真实 agent 任务正确率仍需相应任务集验收。

## 磁盘占用

| --- | ---: | ---: | ---: |
| 65 条记录 | 61,440 B | 61,440 B | 45,056 B |
| 650 条记录 | 139,264 B | 139,264 B | 45,056 B |

均只有一个 `state.sqlite`，没有重复请求快照、逐层文件或遗留 journal。清理后剩数据库结构与本地密钥，不是仍保留的原文副本。基准的临时存档和本次加载的小模型在结束后清理，原有其他模型未被卸载。
