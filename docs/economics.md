# 折叠何时比破坏缓存更省钱

上下文变短不等于费用变低。原请求可能全部享受缓存价，折叠后的请求却需要重新处理，甚至支付缓存写入价。标记、展开和重新发送完整历史还可能增加工具调用、模型往返及输出。因此严格模式要求**下一次完整输入的节省，足以覆盖相对于不折叠完成同一任务所增加的全部工作费用上界**；缺少任一必需边界时保留原文，展示估算和拒绝原因。

这是依赖明确边界的条件证明。它不计入假定的未来节省，不证明展开免费，也不证明回答质量不下降。只有下一次输入费用下降，不能据此声称整个任务净省钱；额外工作无法给出可信有限上界时，完整任务收益就是未知。

## 供应商缓存的实际约束

缓存复用依赖相同的前缀和兼容的请求设置。工具定义、顺序和历史内容都影响匹配；路由、到期和缓存断点也影响实际命中。即使原文前面的内容未改，也不能无条件假设其缓存一定命中。[OpenAI 缓存说明](https://developers.openai.com/api/docs/guides/prompt-caching)

不能把“未命中价格”固定为普通输入价。例如 OpenAI 当前文档对部分模型规定缓存写入价，Claude 也区分读取、短期写入和长期写入。具体价格由模型、服务平台、TTL 和计费档位决定，应使用实际模型的可靠价格边界。[OpenAI 缓存计费](https://developers.openai.com/api/docs/guides/prompt-caching)、[Claude 缓存计费](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

## 不依赖缓存命中的证明

对同一个已经启用本插件、即将发送的请求，比较“保持当前内容”和“应用候选折叠”两个版本，并为折叠导致的全部额外工作预留费用上界。候选版本还要承担本次折叠新增管理提示的输入费用；基线不能为了抵消费用而加入原本没有的提示。设：

| 量 | 必须满足的含义 |
| --- | --- |
| \(L\) | 不进行本次折叠时，完整计费输入 token 数的可信下界 |
| \(U\) | 应用本次折叠后，完整计费输入 token 数的可信上界 |
| \(p_{\min}\) | 原版本可能使用的所有输入计费档位中的最低单价，美元 / 百万 token |
| \(p_{\max}\) | 折叠版本可能使用的所有输入计费档位中的最高单价，美元 / 百万 token |
| \(H\) | 相对于不折叠完成同一任务，尚未计入 \(U\) 的全部新增工作费用的可信上界，美元 |

计数必须覆盖真正发送给供应商并计费的输入，包括系统及开发者指令、工具定义、消息包装、摘要、开头、折叠句柄、附件以及适用的隐藏计费开销。无需计入供应商明确不收费的内容。价格边界必须覆盖缓存读取、普通输入、适用的缓存写入及长度等计费档位，并与当前模型和请求设置一致。

令 \(C_0\) 为原版本的下一次完整输入费用，\(C_1\) 为折叠版本的下一次完整输入费用加上全部新增工作费用，则：

\[
C_0 \ge \frac{L p_{\min}}{10^6},\qquad
C_1 \le \frac{U p_{\max}}{10^6}+H.
\]

相减得到可保证的节省下界：

\[
G=\frac{L p_{\min}-U p_{\max}}{10^6}-H
\le C_0-C_1.
\]

因此只有 **\(G>0\)** 才允许严格模式执行候选折叠。等于零也拒绝。配置了最低节省金额时，还必须严格大于该金额。因为已经同时采用了“原版本全部按最低价收费”和“折叠版本全部按最高价收费”，缓存全部失效也包含在上界内，无需预测实际命中率。

这是充分条件，不是必要条件：没有通过，只表示目前证据不足以保证省钱。实际折叠可能仍然便宜。

仅在全部额外工作有证据被零上界覆盖，即 \(H=0\)，且 token 数精确时，条件可写为：

\[
\frac{T_{\mathrm{after}}}{T_{\mathrm{before}}}
<\frac{p_{\min}}{p_{\max}}.
\]

缓存折扣越大、写入越贵，严格模式要求的压缩幅度就越大。

## 精确示例

下面只是用于演示和测试的价格，不是某个线上模型的报价：普通输入 1 美元 / 百万 token，缓存读取 0.1 美元 / 百万 token，最高写入价 1.25 美元 / 百万 token。原版本下界为 100,000 token，额外费用上界为零。

| 折叠后上界 | 原版本费用下界 | 折叠费用上界 | 节省下界 \(G\) | 决策 |
| --- | --- | --- | --- | --- |
| 7,000 token | $0.01000 | $0.00875 | $0.00125 | 通过 |
| 8,000 token | $0.01000 | $0.01000 | $0 | 拒绝 |
| 60,000 token | $0.01000 | $0.07500 | −$0.06500 | 拒绝 |

第三行虽然少了 40% 的 token，仍不能抵过最坏缓存损失。第一行如果另有 $0.002 的额外费用上界，则 \(G=-0.00075\)，也应拒绝。

第一行若因展开新增一次模型往返，完整重发历史和工具结果合计为 2,000 token，输入价格上界为 1.25 美元 / 百万 token，即使新增输出和工具直接费都为零，也要加 `$0.0025`，使 \(G=-0.00125\)，因此拒绝。`modelRoundTrips: 1` 只描述一次往返，费用来自合计输入 token；不能只计恢复片段本身。

另一个与 [policy 示例](policy.md#a-10000-token-example) 一致的例子：原输入 10,000 token、折叠后 200 token，输入费用节省下界为 `$0.00075`。加 `$0.0001` 固定费、100 个新增输出 token 按 2 美元 / 百万，以及 50 个恢复输入 token 按最高适用价 1.25 美元 / 百万计费，额外费用为 `$0.0003625`，节省下界为 `$0.0003875`。这些费用必须只计在历史预留或 `incremental` 中的一处。

## 为什么默认需要 accounting

`字符数 / 4`、仅对 JSON 字符串分词，或者使用上一轮 token 用量，都不自动构成当前请求的可信边界。供应商实际渲染消息、工具和附件的方式可能不同，部分官方计数接口本身也只返回估算。[Claude token 计数说明](https://platform.claude.com/docs/en/build-with-claude/token-counting)

因此严格模式要求可信的 accounting 来源，例如本地证书程序，或有依据的配置边界。它需要为**同一请求的折叠前后版本**给出完整计费输入的上下界、全部新增工作的费用上界，并绑定模型、请求内容和计费设置。该来源属于用户信任边界；“来自 HTTP 服务”本身不代表计数已经正确或经过供应商认证。

Magpie 在本插件之后还可能运行其他请求钩子、middleware、provider routing 和协议转换。请求 hash 绑定的是本插件当时的候选正文，不是最终供应商请求。Accounting 必须覆盖这些后续变换和所有可能路由的计费上下界；只对中间 JSON 分词不能证明真实账单。当前宿主没有提供让本插件自动校验最终上游请求的接口，因此没有脱离这些前提的全局费用保证。

如果供应商无法提供精确计数，可使用经过验证的保守边界。必须有证据证明下界不会高估、上界不会低估；随意加百分比余量不能代替这项证据。只有估算时可以展示预计 token 和预计节省，但结果应明确为估算，不能标成已经证明。

测试中的本地 fixture 可以为人工构造的计费模型提供精确边界，验证协议和门槛。它不证明真实供应商的 token 数或账单。

## 开销与证明边界

摘要、折叠提示、句柄和工具 schema 如果已包含在下一次折叠后的完整输入中，就计入 \(U\)，不要重复计入 \(H\)。\(H\) 需要覆盖相对于完成同一任务的新增标记、展开、重新固定和后续恢复工作：工具的直接费用、额外模型往返的完整重发历史、工具结果输入，以及新增的可计费输出。工具本身免费也不代表随后一次模型请求免费。

当前 `cost.incremental` 与证书的 `incremental` 都使用以下七个必填字段：

| 字段 | 含义 |
| --- | --- |
| `toolCalls` | 新增工具调用次数上界 |
| `modelRoundTrips` | 新增模型往返次数上界 |
| `inputTokens` | 所有新增完整请求输入 token 的合计上界，包括重发历史和工具结果 |
| `outputTokens` | 所有新增可计费输出 token 的合计上界，包括适用的工具参数、推理和摘要 |
| `inputPricePerMillion` | 新增输入适用的最高单价，覆盖缓存读写及其他档位 |
| `outputPricePerMillion` | 新增输出适用的最高单价 |
| `toolFeesUsd` | 新增工具直接费用的合计上界，美元 |

费用项为 `inputTokens * inputPricePerMillion / 1e6 + outputTokens * outputPricePerMillion / 1e6 + toolFeesUsd`。token 和工具费都是**合计**；`toolCalls`、`modelRoundTrips` 用于说明额外工作的范围，不能再乘一次金额，也不能拿工具次数推导一个通用单价。即使某个次数或 token 数为零，也要显式提供价格和费用边界；未知不等于零。整个 `cost.incremental` 缺失时返回 `policy-incremental-cost-bounds-missing`；对象不完整或参数非法时拒绝配置，证书缺界则拒绝证书。

历史字段 `overheadUsd`、`outputTokens`、`restoreTokens` 仍是额外的费用预留，与 `incremental` **互不重叠**。例如恢复原文的重发输入可以放在 `incremental.inputTokens` 中并把 `restoreTokens` 设为零，也可以只放进 `restoreTokens`；不要两边重复计费。恢复输入按输入、缓存读取和缓存写入适用上界的最大值收费。历史字段兼容性默认零是调用者的条件假设，不是已经测得免费。

已经生成并计费的原始助手输出是沉没成本，折叠不能退回这笔费用。已经发生的标记调用在“从现在起是否折叠”的决策中同样是沉没成本，但评估整个折叠操作或插件的净收益时必须计入，不能隐去。输出长度变化也要用新增输出上界覆盖。

若恢复次数、完整重发输入、输出或直接费用中的任何一项无法给出可信有限上界，就无法证明完成同一任务的净收益，应拒绝严格折叠。按实际使用记录这些操作，逐次评估新的折叠；不借用假定的未来请求次数作为今天的保证。

折叠摘要可能遗漏信息。保留原文和提供逐项展开工具解决了可恢复性，不构成语义无损或回答质量不下降的数学证明。

## 本地经济分析脚本

`scripts/economic-analysis.py` 只对提供的文本做 `o200k_base` BPE 计数，按参考价格计算条件费用，不调用模型，也不生成完整供应商输入证书。输出 schema 为版本 2；历史 benchmark 数据保持原样，其中旧的默认零成本结果不能当作当前完整工作成本证明。脚本内官方价格是 **2026-10-26 的历史快照**，并非实时价格；另一组价格是合成示例。新增工作的输入、输出单价上界必须用参数另行显式提供，不会从历史快照推断实际服务价格。

输入格式示例：

```json
{
  "prompts": [
    { "label": "original", "text": "完整的待比较原始文本" },
    { "label": "folded", "text": "实际折叠后的文本", "markOutputTokens": 0 }
  ]
}
```

每个后续 prompt 的 `markOutputTokens` 或 `markOutputText` 表示产生该层标记的历史费用预留，二选一。未提供时为未知，不再默认零。如果标记输出已经全部包含在新增工作 `incremental.outputTokens` 中，此处显式填零以避免重复。文本计数不覆盖输出包装或推理等其他收费内容，应在相应预留中补齐。原始 prompt 不能携带非零标记费用。

在已有含 `tiktoken` 的 Python 环境中运行，例如下面显式声明所有额外成本均由零上界覆盖；这些零必须有实际依据：

```sh
python scripts/economic-analysis.py --input prompts.json \
  --extra-cost-usd 0 --unfold-input-tokens 0 --unfold-output-tokens 0 \
  --incremental-tool-calls 0 --incremental-model-round-trips 0 \
  --incremental-input-tokens 0 --incremental-output-tokens 0 \
  --incremental-input-price-per-million 1.25 \
  --incremental-output-price-per-million 2 \
  --incremental-tool-fees-usd 0
```

`--incremental-tool-calls`、`--incremental-model-round-trips` 是新增工作次数上界，其余五个 `--incremental-*` 参数分别对应同名 camelCase 字段的合计 token、价格和合计费用。输入 token 必须包含完整重发历史和工具结果。`--extra-cost-usd`、`--unfold-input-tokens`、`--unfold-output-tokens` 是历史预留，必须与标记费用及新增工作互不重叠；恢复输入按参考场景所有适用输入价的最大值收费。所有这些参数省略都表示未知，显式零才表示调用者提供了零上界；非法、负数、非有限费用或非安全整数计数会被拒绝。

每个参考价格场景分别输出 `input_only_H_zero`、`marking_output_only`、`marking_plus_configured_reserves` 和 `full_work_cost`。前三项是有意排除部分工作的假设场景，不能证明整个任务省钱。`full_work_cost` 只要缺少标记、历史预留或七个 incremental 字段中的任一必需边界，就返回 `status: "unknown"`、`missing_bounds`，金额及严格门槛判断均为 `null`。即使参数齐全且条件收益为正，文本范围仍不等于完整供应商请求证据，因此 `provider_task_saving_proven` 始终为 `false`。

相邻层比较只计当前层标记，原始到当前层比较累计标记；任一层标记未知会传递到相应累计结果。CLI 的历史预留与 incremental 参数是**每个显示比较的整体上界**，不会按层数或调用次数重复相乘。需要分别保证它覆盖相邻比较和累计比较中的全部新增工作。两种视图是同一次假想下一输入的替代比较，不能将各行节省相加，也不计入想象中的未来节省。

## 更宽松的前缀公式为什么不是默认保证

如果有独立证据保证未改前缀在两种版本中的缓存计费完全相同，可以抵消该前缀的费用。令首次改动之后的原长度为 \(B\)，净减少 \(D\) token，读取价为 \(r\)，未命中最高价为 \(w\)，则充分条件为：

\[
Dr > (B-D)(w-r)+10^6 H.
\]

左侧是移除 token 至少省下的读取费用，右侧是保留后缀重新处理的最坏额外费用及开销。这个条件通常比全请求边界宽松，但“未改前缀一定按相同方式计费”是额外前提，不能只因为文本没改就视为成立。

## 实现时应保留的审计信息

每次决策至少记录模型和请求身份、边界来源、\(L\)、\(U\)、\(p_{\min}\)、\(p_{\max}\)、历史预留、完整 `incremental`、总 \(H\)、两种费用边界、\(G\) 以及通过或拒绝的原因。次数、合计 token、价格或费用边界缺失，模型不匹配，请求已改变，边界过期，非有限数或负数时拒绝执行新折叠。

实现按证书中数值的规范化十进制表示进行 BigInt 定点比较，避免浮点误差把恰好收支平衡判成盈利。返回的金额数字向保守方向取整；数值溢出或小到无法可靠表示时也不放行。

收益测试至少覆盖严格等于零时拒绝、未知价格时拒绝、较小 token 上界不会降低收益、较高写入价或额外开销不会增加收益，以及上述四个数值示例。
