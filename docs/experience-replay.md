# 体验回放：短内容跳过，查阅不撤销折叠

这份回执比较同一组输入经过旧版和改版请求钩子后的大小。它验证的是**完整请求投影、归档恢复和默认工具行为**，没有调用模型或供应商，不能据此推断任务正确率、延迟或实际账单。

## 版本与输入

- 基线：`8fd0bf70dc2729b3662e3112c522698af0b2847f`。
- 改版：与本回执一起提交的源码；默认 `delayRequests=1`、`minSavingTokens=256`，未配置模型容量。
- 运行时：Bun `1.4.4`；TypeScript 检查使用仓库锁定的依赖。
- 脚本：[scripts/replay-experience.ts](../scripts/replay-experience.ts)。
- 协议：Chat Completions 风格完整历史；每个请求包含该版本真实的 `context_folding` 工具描述和参数 schema。
- 源码材料：仓库实际 `src/source.ts`，4,092 字节，SHA-256 为 `675d651c5dfc40443f16679d1e80d3c78bf57b1397540592b8cc24d9f44158b5`。
- 审阅材料：脚本中的确定性公开审阅 fixture，2,917 个 UTF-16 单元、7,671 个 UTF-8 字节，SHA-256 为 `781083cb4565ba1e10914038afe763a602c74dded0632f9393ab39b01df6edbd`。这是模拟已完成工作的测试材料，不是一次真实模型审阅的记录。

两边使用相同内容与相同请求顺序。`--plugin-root` 只替换被测实现，源码 fixture 仍由同一个回放脚本读取。每个场景使用独立临时归档，结束后清理，不接触真实会话。

## 怎么算

所有 token 数均为 `ceil(JSON UTF-8 bytes / 4)`，正数表示缩短，负数表示增加。

脚本给出三种不同口径，避免把开销藏在基线里：

1. **请求钩子净差**：本次完整输入请求减去完整输出请求，包含引用和恢复定位提示。这适合检查折叠本身有没有把请求变大。
2. **扣除回读开销后的净差**：比较不含本插件查询消息的原历史与实际输出。`read`/`restore` 的调用参数、消息外壳、正文和元数据都计入成本；它们仍留在后续历史中时，再次计入。
3. **再扣除工具声明后的净差**：在第二项的原历史中移除 `context_folding` 声明，再与实际输出比较。这把常驻工具定义的成本也算进去。比较保留相同的业务内容和源码注释，不把它称为完全重建的“无插件用户行为”。

两次完整原文读取只用于校验，单独记录在 `exactRecoveryValidation`，不注入被测工作流，也不混入工作流节省总数。它们合计返回约 3,093 估算 tokens 的序列化结果；这项成本在两边相同。

## 空闲与原体验中的短笔记

| 场景 | 请求数 | 原版请求钩子累计净差 | 改版请求钩子累计净差 | 改版归档条目 |
| --- | ---: | ---: | ---: | ---: |
| 无标记的普通推进 | 5 | -281 | 0 | 0 |
| 用户体验记录中的两段短中文笔记 | 3 | -74 | 0 | 0 |

原版在等待和空闲请求中也追加预算提示；两段短笔记被折叠后，每次完整请求仍增加约 9 tokens。改版直接保留这两段短笔记，原因记录为 `insufficient-savings`，没有为了演示创建归档。

**零动态提示开销不等于插件完全不占上下文。** 工具描述和 schema 依然需要由宿主提供。按脚本的声明对象口径，工具定义由约 1,190 降到 866 估算 tokens；计算完整请求中移除该工具后的差额，改版约为 874 tokens/次。因此没有可折叠工作时，启用工具仍然存在固定成本。

## 已完成的源码审阅与分页查阅

长工作流包括一份实际源文件读取、一段明确标记为已完成的审阅记录，以及留在标记外的结论。通用 `exec` 结果、调用 ID、参数和用户要求始终保留。

| 请求 | 原版输入 | 原版输出 | 改版输入 | 改版输出 |
| --- | ---: | ---: | ---: | ---: |
| 首次观察闭合标记 | 4,562 | 4,618 | 4,238 | 4,238 |
| 下一次请求，满足默认延迟 | 4,601 | 1,806 | 4,278 | 1,456 |
| 后续工作 1 | 4,641 | 1,846 | 4,317 | 1,496 |
| 后续工作 2 | 4,680 | 1,885 | 4,357 | 1,535 |
| 默认 `read` 后继续 | 6,843 | 5,974 | 5,866 | 3,045 |
| 显式恢复后继续 | 7,107 | 6,238 | 6,128 | 5,233 |

输入大小不同是因为真实工具定义和实际返回页大小不同；内容 fixture 相同。首次观察保留原文，后续三次正常推进中，改版每次请求钩子净减少约 2,821–2,822 估算 tokens。

### 默认 read 的差别

| 指标 | 原版 | 改版 |
| --- | ---: | ---: |
| 默认返回的 UTF-16 单元 | 2,917（全文） | 2,000（第一页） |
| `nextOffset` | `null` | `2000` |
| `kept` | `true` | `false` |
| 读回结果估算 tokens，含序列化 | 2,035 | 1,383 |
| 其中元数据和额外序列化开销 | 102 | 98 |
| 后续仍折叠的条目 | 1 | 2 |
| 后续请求净差，扣除回读历史开销 | -1,254 | +1,351 |
| 上一项再扣除工具声明成本 | -2,452 | +477 |

原版默认读取会将审阅条目标为持续展开，下一次原历史与读回内容同时进入请求。改版只返回所需页，原历史中的条目继续保持折叠；这里连常驻工具声明、调用参数和返回页一起算，后续请求仍然比对照小。

### 六次请求的累计结果

| 口径 | 原版 | 改版 |
| --- | ---: | ---: |
| 请求钩子累计净差 | +10,067 | +12,181 |
| 扣除回读历史开销 | +5,557 | +8,979 |
| 再扣除工具声明成本 | -1,629 | +3,735 |

最后一步故意要求持续展开审阅原文，用于验证显式 `restore`。在该步骤中，改版扣除回读开销后的净差为 -837，再扣除工具声明后为 -1,711。恢复原文会消耗空间，这是调用方明确选择的行为，不能把这一笔从报告中删掉。旧版没有 `restore` action，所以对照使用等价的 `read(peek:false)`。

## 自动校验了什么

运行带 `--expect-improved` 的脚本会检查：

- 空闲请求不新增动态提示；短演示文本不折叠、不创建归档。
- 默认延迟之后，长审阅文本与可信来源的源码结果都形成可恢复引用。
- 折叠后的完整请求净差满足 256 估算 tokens 的门槛。
- 系统约束、全部用户消息、工具调用名称/参数、调用结果 ID 和显式结论保持完整。
- 默认读取只返回第一页，不让原条目持续展开；加上回读消息之后，工作流仍然变短。
- 两份归档的完整工具读取与原始 fixture 逐字一致，SHA-256 相符。
- 显式恢复之后，下一次请求重新保留该审阅原文。
- 请求钩子没有原地修改客户端传入的历史。

这不是宿主 GUI 安装测试，也不证明所有协议、所有任务或所有文本分布都有相同收益。其他协议与并发等合同由仓库回归测试覆盖。

## 复现

在装好仓库依赖和 Bun 后运行：

```sh
bun scripts/replay-experience.ts --expect-improved > /tmp/context-folding-after.json
```

如果本地 Git 包含基线提交，可以创建独立对照工作树并复用已安装依赖：

```sh
git worktree add --detach /tmp/context-folding-before 8fd0bf70dc2729b3662e3112c522698af0b2847f
ln -s "$PWD/node_modules" /tmp/context-folding-before/node_modules
bun scripts/replay-experience.ts --plugin-root /tmp/context-folding-before > /tmp/context-folding-before.json
```

脚本只把 JSON 报告写到标准输出。完整每请求数据、工具声明大小、分页数据、恢复校验及累计指标都在输出中；更改 fixture 或工具 schema 后应重新生成结果，不能继续沿用本页数字。
