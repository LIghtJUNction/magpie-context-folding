# 用量、速度与任务质量迭代

本轮固定 `codex/gpt-6-luna`，不降低模型档位或推理强度。把任务正确率、实际请求用量与耗时一起记录；没有渠道账单或当前费率时，不把 token 或字节换算成美元。

## 已有轨迹的基线

2026-10-28 的十二层回归任务，两组初始验证均返回 stderr 26,602 UTF-8 字节，控制器原先把它全部加入首轮用户消息。最终通过的测试命令也返回约 30 KB 工具内容。

| 上轮独立任务 | 请求 | 输入 token | 缓存输入 | 未缓存输入 | 输出 token |
| --- | ---: | ---: | ---: | ---: | ---: |
| baseline | 11 | 199,839 | 170,112 | 29,727 | 2,394 |
| folding | 5 | 87,136 | 60,928 | 26,208 | 1,813 |

两组都没有实际对话折叠，修改过程也不同，不能把差异归因于折叠。这个基线只用于定位开销，不是优化后的成绩。

## 本轮改动

1. 新增可选的 `--verification-output summary`：初始验证通过时，只给模型退出码、测试汇总、输出字节数和完整日志路径。完整日志仍保存在沙箱内，可按需读取；失败输出完整保留。默认仍是 `full`，因为当前小样本没有证明摘要模式保持任务质量。
2. 归档叶节点不含子引用时，`archiveView` 直接返回原文，避免每次查询都构建全库索引。嵌套节点仍走原有路径。
3. 增加每次模型 HTTP 请求的耗时记录；将实际模型时间与工具、验证、归档处理区分开，避免把本机测试时间误当推理时间。
4. 对比试验使用同一冻结源码，重复尝试时交替 full/summary 的执行顺序。依赖和运行时只读复用，运行期间不得升级。

## 质量检查与复现

```sh
npm run bench:tree
npm run bench:quality -- --output .local-tests/luna-quality-example
```

`bench:tree` 使用 Git HEAD 和当前查询代码，以同一组 3,000 个归档叶节点执行无匹配查询，预热后交替五轮并校验完整输出相同。它排除存储 I/O 和模型时间，不能据此宣称所有 agent 任务加速相同比例。

| 场景 | 优化前中位数 | 优化后中位数 |
| --- | ---: | ---: |
| browse 无匹配搜索 | 716.36 ms | 2.26 ms |
| grep 无匹配搜索 | 834.69 ms | 2.46 ms |

以上为本轮本机一次五轮交替基准的中位数；完整样本与源码摘要随结果 JSON 保存。

`bench:quality` 比较 full/summary 的初始日志披露，默认各两次，共四个 Luna trial，每次最多十次请求。任务是理解本项目的六个集成边界：偏移单位、普通读取是否恢复、嵌套 resolve、可调用恢复工具、删除保护、共享子节点恢复。答案需要逐项引用真实源码；独立检查器核对选项及引用确实存在。该评分只能说明这些仓库合同题的表现，不能代表通用智力或证明引文解释充分。

标准答案脚本从模型沙箱排除，模型只拿到问题；后验在干净副本中只导入允许的交付文件再执行，避免把工作目录缓存作为评分环境。首次探索运行曾暴露标准答案脚本可见问题，已停止，结果不进入正式比较。所有失败尝试仍计入本轮消耗记录。

## 正式日志披露对照

隐藏标准答案、干净验收的四次试验均未达到六题全对且正常完成的标准。full 两次均答对 4/6，一次达到请求上限，一次正常结束；summary 一次首请求 HTTP 502，另一次在十次请求内没有交付。失败未重试、未剔除。

摘要消息从 27,180 字节降至 219 字节，但这只能证明初始输入变小，不能证明每个成功任务更便宜。默认仍保留 full；summary 为显式可选项。

新增可选 `--candidate-feedback`：模型可在交付前至多两次调用独立检查器，在干净副本得到逐项通过／失败反馈。它不返回标准答案，输出只作为本任务的纠错信号；工具带来的额外轮数和用量也计入结果。可用以下入口测试：

```sh
npm run bench:quality -- --output .local-tests/luna-feedback-example --candidate-feedback
```

该组使用 summary 日志和最多十四次请求，与十次请求的无反馈试验预算不同，结果必须同时报告预算和用量；不能声称仅加入反馈就证明普遍智力提升。

两次反馈试验均正常结束并获得 6/6，分别使用 12 和 9 次请求。第一组实际执行两次检查，收到 4/6、5/6 后修正到最终 6/6；第三次检查请求被额度限制，没有执行。第二组执行两次检查，最终亦为 6/6。

| 反馈试验 | 输入 token | 缓存输入 token | 输出 token | 模型 HTTP 总耗时 | 完整 trial 耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 352,958 | 307,328 | 2,217 | 91.31 s | 121.42 s |
| 2 | 214,514 | 186,752 | 1,963 | 91.09 s | 122.84 s |

它支持保留有检查器任务的可选纠错入口；没有证明所有任务更省更快。最终离线验收：根项目 254 项、Python 核心 169 项、控制器 13 项全部通过；单独递归套件 73 项为全套子集，不相加。

正式失败样本和全部用量见 [cost-speed-quality-results.json](cost-speed-quality-results.json)。

小样本的模型随机性、服务端缓存与调度波动仍存在。只有正确率不下降时，才考虑保留降低输入的配置；观察不到稳定改进时，报告实际值，不把单次波动写成省钱保证。
